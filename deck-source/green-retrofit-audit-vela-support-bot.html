1 · Hook

Every chat message wakes four paid services, and the widget keeps knocking after the chat ends

The artifact

A website support chat for Vela, a fictional personal-finance app. An n8n RAG agent answers from the Notion help pages (Pinecone search + Cohere rerank + OpenAI). When the docs run out, it escalates to a human on Telegram, and the human's reply is delivered back into the chat.

Source: week-5/lab-multi-app-integration · github.com/benmayer/lab-multi-app-integration · live at tools.ben-mayer.com/support-bot

Audience for this deck: Vela's CTO, who decides whether we fix this before launch.

Cost

OpenAI, Cohere, Pinecone and n8n executions are each billed per call. Wasted calls cost money before they cost carbon.

Risk

Idle traffic eats n8n execution quotas and buries real failures in log noise.

Reputation

A finance brand that says "green" without numbers invites a greenwashing headline.

2 · One unit of value

R = one resolved support conversation

A visitor's question answered in the chat, either by the bot from the docs or by a human reply delivered back into the same chat.

Why this R

  • It is what Vela pays support for: a closed contact.
  • Per message would reward a chatty bot that needs more turns.
  • Per visitor would hide cost, because most visitors never open the chat.
  • Countable today: no escalation, or an escalation row with delivered = true.

SCI-style score

SCI = (E × I + M) per R

Inside the boundary: n8n instance, OpenAI chat + embeddings, Cohere rerank, Pinecone, the Data Table, the widget's polling.

Outside, for v1: visitor devices, Notion and Telegram infrastructure, model training, and vendor hardware (M), because we have no data on them.

H1

Model calls

At least 2 LLM calls per turn and 3+ on an escalation turn. GPU inference is the largest energy item per call.

Idle polling

Up to 360 n8n executions per conversation. Almost all return "no reply yet", and polling continues after the reply arrives.

Repeated work

"How much is Pro?" is embedded, searched, reranked and answered from scratch every time. Caching candidate.

H4

Stored waste

Every poll is saved as an execution, Pinecone holds duplicate chunks for one page, and escalation rows never expire.

4 · Assessment defense: the skeptic's question

"Why should we believe this?" The locations are proven, the sizes are not yet

Evidence  from the code, config and one real trace

  • Widget: POLL_EVERY_MS = 5000, POLL_MAX_MS = 30 min. startPolling() runs after every message and never stops on a reply.
  • Agent config: gpt-5.4-mini, Pinecone as a tool (top-K 5) with Cohere rerank, buffer memory. That means 2 model calls per searched turn.
  • Trace #2204: escalation saved 11:45:07, reply 11:45:50, delivered 11:45:54. About 9 polls to deliver one reply.

Not measured  yet

  • Tokens per turn, energy per call, grid intensity per provider region.
  • n8n prunes executions: only 1 is retained right now (a Notion DNS error on 15 Nov). There is no history to measure from.

7 · Solution 1 of 5
Quick win · ~2 hours

Poll only after an escalation, and stop when the reply lands

Problem H2

The widget polls n8n every 5 s for 30 min after every message, even when nothing was escalated and after the reply has arrived.

→

Change

The chat response returns an escalated flag, and polling starts only then. Stop on the first reply. Back off 5 → 15 → 30 s. Later: push via a small Worker (SSE).

→

Expected effect

Non-escalated R: up to 360 → 0 polls.
Escalated R (like #2204): up to ~370 → ~6.
Business: fewer n8n executions against quota, cleaner logs.

Pillars
EnergyHardware
GSF pattern

Keep request counts low

Tradeoff, honestly

A human reply can show up to 30 s later. Each poll is cheap, so this mostly saves count and cost, not the biggest energy item.

8 · Solution 2 of 5
Medium · after baseline

Answer repeated FAQ questions from a cache

Problem H3

"How much is Pro?" runs embed → search → rerank → 2 LLM calls every time, although the answer only changes when a Notion page changes.

→

Change

Reuse the query embedding we already compute. If a cached question is ≥ 0.95 similar, return its answer. Tag each entry with its Notion pageId; the existing update trigger clears that page's entries.

→

Quality check

Each week, grade 20 random cache hits against a fresh answer. Only cache answers that came from the docs, never escalations.

Pillars
EnergyCarbon
GSF pattern

Cache static data

What I don't know

The hit rate. FAQ traffic usually repeats, but we have no logs. Build it only if week 1 shows the top 20 questions cover a large share of turns.

9 · Solution 3 of 5
Medium · biggest energy lever

Fewer, leaner model calls per turn, gated by a quality test

Problem H1

The agent pattern uses one LLM call to decide to search and a second to answer. Each call carries 5 chunks and the whole memory window. "Yes, please" turns pay the same.

Change

  • Retrieve first, then one LLM call. Keep the agent only for the escalation tools.
  • Rerank wide, send the top 3 to the model.
  • Skip retrieval for short confirmations ("yes", "thanks").
  • Keep gpt-5.4-mini. Try a smaller model for routing only if it passes the test set. No blind downgrade.
Pillars
EnergyHardwareCarbon
GSF patterns

Optimize agent orchestration to reduce unnecessary model calls · Use right-sized and energy-efficient AI models

Quality gate

30-question golden set from the Notion FAQ: correctness and escalation decisions must not get worse.

10 · Solution 4 of 5
Quick win · ~half a day

Stop storing what nobody reads, but keep the counts

Problem H4

Every empty poll is saved as an execution. Pinecone holds duplicate chunks from early test runs. Escalation rows (visitor questions) are kept forever.

→

Change

Move polling into its own workflow with save successful executions off, and write a daily count to a metrics table instead. Use deterministic chunk ids (pageId + index) so re-ingest overwrites. Purge duplicates. Delete delivered escalations after 30 days.

→

Side benefits

Retrieval stops wasting top-K slots on duplicates. The 30-day expiry is also GDPR data minimisation for visitor questions.

Pillars
HardwareMeasurement
GSF patterns

Delete or auto-expire unused storage · Remove unused assets

Tradeoff

Fewer raw logs to debug from. That is why counters replace them: deleting evidence must not break the measurement plan.

11 · Solution 5 of 5
Strategic · after baseline

Run the workload where the grid is cleaner and the users are

Problem

We do not know I. Pinecone is probably in us-east-1 and the n8n host region is unknown, so EU visitors' requests may cross the Atlantic twice per turn.

→

Change

Put n8n and Pinecone in one EU region, chosen with grid-intensity data (e.g. Electricity Maps), preferring a low-carbon grid where the provider offers it. Check OpenAI's EU data-residency options. Time-shift full re-embedding jobs to low-intensity hours.

→

Why it is last

It lowers I for every call, but it is a migration with plan and vendor limits. Re-embedding is rare, so time-shifting it saves little. Do it once the baseline shows E per R.

Pillars
CarbonMeasurement
GSF patterns

Choose the region that is closest to users · Use carbon-aware scheduling and region selection for AI workloads

Business link

EU hosting also helps with data-residency questions from a finance client, and cuts latency.

14 · Caveats and next steps

What this deck does not claim, and what we validate next

  • No "carbon neutral" and no kg CO₂e figure. E is not measured yet. We will report SCI as a range with a stated boundary.
  • Offsets don't lower SCI. SCI only counts reductions, so buying offsets would not move the score, and we would not present them as one.
  • Polling is big by count, small per call. Model tokens probably dominate energy, so S3 matters more than its numbers suggest.
  • Leaner context can hurt answers. The golden set gates every change.

Validate next, with whom

  • n8n host region and execution retention: Ironhack platform team
  • Pinecone index region: Pinecone console
  • OpenAI EU residency and usage export: Vela account owner
  • Real escalation rate and turns per R: week-1 baseline

Ask: approve the 2-week trial: baseline first, then S1 + S4 (about one day of work) and a first cut of S3 behind the golden set.
